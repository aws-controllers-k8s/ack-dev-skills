# Review ACK PR

You review pull requests against ACK controller repos with deep domain knowledge of the ACK code generation pipeline, runtime framework, and common pitfalls.

## Input

The user provides a PR URL or `<org>/<repo>#<number>`. Parse accordingly:
- Full URL: `https://github.com/<org>/<repo>/pull/<number>`
- Short form: `<org>/<repo>#<number>` or just `#<number>` (infer repo from CWD)

## Phase 1: Gather Context

### Step 1: Fetch PR metadata and diff

```bash
gh pr view <URL-or-number> --repo <org>/<repo> --json title,body,labels,baseRefName,headRefName,files,additions,deletions,commits
gh pr diff <URL-or-number> --repo <org>/<repo>
```

### Step 2: Fetch review comments (if any)

```bash
gh api repos/<org>/<repo>/pulls/<number>/comments --jq '.[] | {user: .user.login, path: .path, line: .line, body: .body}'
gh api repos/<org>/<repo>/pulls/<number>/reviews --jq '.[] | {user: .user.login, state: .state, body: .body}'
```

If there are existing review comments:
- **Read them carefully before starting your own review.** Reviewers may have already identified issues, requested changes, or had discussions with the author that affect what's still outstanding.
- Track which comments have been addressed (look for subsequent commits after the comment timestamp, or author replies indicating the fix).
- In your review output, include a "Prior Review Comments" section summarizing the status of existing feedback (resolved, still open, or disagreed-with).
- If a reviewer requested a change that you agree with and it hasn't been addressed, promote it to a Blocker or Suggestion in your findings.
- If a reviewer requested a change that you disagree with, note your reasoning in the review.

### Step 3: Identify the controller and linked issue

- From the repo name (e.g., `rds-controller` → service `rds`)
- From PR body — look for `Resolves`, `Fixes`, `Closes` links to community issues
- If linked issue found, fetch it for context: `gh issue view <number> --repo aws-controllers-k8s/community --json title,body,labels`

### Step 4: Ensure the controller repo is available locally

```bash
bash ../resolve-issue/scripts/ensure-repo.sh <name>-controller
```

(The `resolve-issue` skill ships the shared `ensure-repo.sh` helper; it clones/forks/pulls the controller repo. If you don't have that skill installed, clone the repo manually.)

## Phase 2: ACK-Specific Review

### Check 0: Scope — One Resource Per PR

- A PR must only add/modify ONE resource. If a PR adds multiple new resources (e.g., both `ResourceA` and `ResourceB` CRDs) → **BLOCKER**
- Each resource should be its own separate PR, even if they were requested in the same issue
- Exception: changes that naturally span resources (e.g., adding a cross-resource reference field, shared utility code) are fine

### Check 1: Generated vs Hand-Written File Boundaries

- Files marked `// Code generated by ack-generate. DO NOT EDIT.` must NOT be hand-edited
- Acceptable generated file changes: only if they come from regeneration after `generator.yaml` or template changes
- If the PR edits generated files without corresponding `generator.yaml`/template changes → **BLOCKER**

### Check 2: generator.yaml Correctness

If `generator.yaml` is modified, verify:

| Aspect | What to check |
|--------|--------------|
| `from.operation` | Does the referenced operation actually exist in the SDK? Does the `path` match a real field? |
| `renames` | Are renames applied to ALL operations that use the field? Missing one causes silent mismatches |
| `references` | Does `path` point to a valid field on the referenced resource? Is `service_name` needed? |
| `late_initialize` | Must include `skip_incomplete_check: {}` — flag this if missing |
| `compare.is_ignored` | Is there a corresponding `delta_pre_compare` hook that manually compares? If not → drift |
| `synced.when` | Does the status field path actually exist in the CRD Status? |
| `exceptions.errors.404.code` | Is this the actual error code from the SDK, not a guess? |
| `tags.ignore` | Only set if the resource truly has no tag operations |
| `is_immutable` | Only for fields that AWS will reject on update, not just fields we prefer not to change |
| `update_operation.custom_method_name` | Is the method actually implemented? Does it handle all delta fields? |
| `is_read_only` | Should NOT be added for Describe-only output fields — the code-generator infers placement automatically. Flag redundant `is_read_only`. |

### Check 3: Custom Update Payload Completeness

If `custom_update.go` or `newCustomUpdateRequestPayload` is modified:

- Every new Spec field added to `generator.yaml` that's mutable must be wired into the custom update payload
- Pattern: `if desired.ko.Spec.X != nil && delta.DifferentAt("Spec.X") { res.X = desired.ko.Spec.X }`
- Fields that only make sense in combination with other fields (e.g., `DBInstanceParameterGroupName` only with `EngineVersion`) should be nested inside the other field's condition
- Check `AllowMajorVersionUpgrade` and `ApplyImmediately` are still being set (override_values)

### Check 4: Delta / Comparison Logic

If `delta.go` or `delta_pre_compare` hooks are modified:

- Fields with `compare.is_ignored: true` MUST have manual comparison in `delta_pre_compare` — otherwise updates are silently lost
- `ackcompare.HasNilDifference` must be checked BEFORE value comparison (nil dereference risk)
- Normalization in `delta_pre_compare` (setting `a.ko.Spec.X = b.ko.Spec.X` to suppress diffs) should only suppress cosmetic diffs, never real state changes

### Check 5: Hook Templates (.go.tpl)

If template hooks are added/modified:

- Template must compile — check for unmatched braces, missing `{{ end }}`, typos in field names
- Nil checks before pointer dereferences — AWS SDK fields are all pointers
- Hook placement matters: `pre_build_request` can short-circuit, `post_build_request` can modify input, `post_set_output` can modify the resource object
- Correct variable name per hook point: `sdk_create_*` → `desired`, `sdk_read_one_*` → `ko`, `sdk_update_*` → `desired`/`latest`, `sdk_delete_*` → `r`
- Custom error returns: use `ackerr.Terminal` for permanent failures, `requeueWaitWhile*` for transient states
- Hooks should be a last resort — flag any hook that duplicates a declarative `generator.yaml` capability (`synced.when`, `is_immutable`, `terminal_codes`, `late_initialize`, `is_iam_policy`)

### Check 6: CRD Compatibility

If CRD YAML files changed (`config/crd/bases/`, `helm/crds/`):

- New optional fields are backwards-compatible (OK)
- Removing fields, changing types, or making optional fields required → **BREAKING CHANGE / BLOCKER**
- Check that `+kubebuilder:validation` markers on new fields are correct

### Check 7: Cross-Resource References

If `references` are added:

- The referenced resource must exist in the same controller OR have `service_name` set
- The `path` must be a real field (typically `Status.ACKResourceMetadata.ARN` or `Spec.Name` or `Status.ID`)
- Adding a reference generates a `*Ref` field — verify the generated code resolves it correctly

### Check 8: Test Coverage

- Custom Go code (hooks, custom_update) should have unit tests
- If `custom_update.go` adds a new field path, there should be a test with that field in the delta
- If `delta_pre_compare` adds custom comparison, there should be a test verifying both "diff detected" and "diff suppressed" cases
- E2e tests are only needed when changes produce observable AWS state (see below)

**When e2e tests are NOT needed:**
- Write-only fields not returned by Describe
- One-time trigger parameters (only meaningful during a specific operation)
- Behavior fully covered by unit tests with no additional integration value

## Phase 3: General Go Quality

### Check 9: Error Handling

- No swallowed errors (empty `if err != nil {}` blocks)
- Errors wrapped with context where appropriate
- Terminal vs retriable errors classified correctly. Only errors that require a spec change should be terminal — never access/auth errors.

### Check 10: Nil Safety

- All AWS SDK pointer fields nil-checked before dereference
- Nested struct access guarded at each level (e.g., `if resp.X != nil && resp.X.Y != nil`)

### Check 11: Code Style

- No unnecessary comments — especially not on generated code
- Consistent naming with existing code in the same file/package
- No unused imports, variables, or dead code
- Conventional commit message format: `fix:` / `feat:` / `chore:`

### Check 12: Commit Hygiene

- Commit message references the community issue (`Resolves aws-controllers-k8s/community#XXXX`)
- Single logical change per commit (no unrelated formatting changes mixed in)

## Rules

- Do NOT approve or comment on the PR via GitHub — this is a LOCAL review only
- Do NOT push, create branches, or modify code
- If the PR is against a repo you don't have locally, clone it first (via `ensure-repo.sh` or manually)
- Be specific — cite file paths and line numbers for every finding
- Distinguish between "the code is wrong" (blocker) and "I'd do it differently" (nit)
- If the PR looks correct but you're uncertain about a specific AWS API behavior, say so explicitly rather than guessing
- For large PRs (>500 lines), focus on the hand-written code; skim generated changes for consistency but don't review them line-by-line
