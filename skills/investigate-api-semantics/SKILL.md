# API Semantics Investigation

## Overview

An ACK controller is only as correct as its author's knowledge of the AWS API it drives: asynchronous state machines,
one-change-per-call rules, sub-resource APIs, server defaults, stale responses, error-code oddities, tag semantics,
quotas and cooldowns. This skill runs a blind, measurable, re-runnable investigation of one service with the
[aws-api-semantics](https://github.com/aws-controllers-k8s/aws-api-semantics) lab and turns the result into documentation agents and humans read before planning or reviewing.

Three artifacts, in this order of authority:

| artifact | where | role |
|---|---|---|
| findings (YAML, schema-validated) + probe evidence | lab repo `services/<svc>/findings/*.yaml`, `services/<svc>/probes/**` | canonical source; every finding points at the probe that produced it |
| rendered docs | `CONTROLLER_DIR/docs/api-semantics/` (`README.md` load guide, `index.md`, `service.md`, one doc per resource area, `details/`) | regenerated by `semantics render`; hand-written text only in preserved blocks or `supplementary/` |
| pointer | `CONTROLLER_DIR/AGENTS.md` marked block (+ `CLAUDE.md` -> `@AGENTS.md`) | tells agents the docs exist and how to load them; no controller README changes |

The method (pilot: DynamoDB, 548 findings, 97% recall against the controller's own hooks catalog, 23 stale controller
beliefs corrected) is documented in the lab's `METHOD-REVIEW.md` and `METHOD-LOG.md`; every rule below cites them.
Paths below are relative to the lab repo root or to `CONTROLLER_DIR`. `semantics` is `python cli/semantics.py` in the lab.

Edit authored fragments, plans, scoring notes and findings, then run the relevant CLI command. Generated hypothesis
catalogs, shards, digests, seeds, samples and reports are not hand-edited.

## Intake

Ask or confirm, then write the answers into `services/<svc>/STATUS.md` (never into this skill or any brief):

1. **Service and prefix**: AWS service name as botocore knows it, finding-id prefix (2-6 upper-case chars).
2. **AWS access**: profile or role to export as `AWS_API_SEMANTICS_PROFILE`; how the operator refreshes credentials is their
   environment. The harness pauses probes on expiry (`PAUSED`, exit 75); `semantics probe resume-paused --all` continues.
3. **Regions**: primary and secondary (`AWS_API_SEMANTICS_PRIMARY_REGION`, `AWS_API_SEMANTICS_SECONDARY_REGION`); cross-region families need both.
4. **Disposability**: the account must be disposable. Probes are destructive, create billable resources, burn quotas and
   cooldowns (24 h / 30 d), and leave mandatory-retention leftovers (7-day KMS deletions, system backups). Get an
   explicit yes.
5. **Lab repo path** (`AWS_API_SEMANTICS_LAB`): the `aws-api-semantics` checkout, and whether a `.venv` with `boto3 pyyaml jsonschema` exists.
6. **Controller dir(s)** (`CONTROLLER_DIR`): may be absent for a service with no controller yet (then no ground truth).
7. **Mode**: full / update / verify (see Modes) and any budget cap (wall-clock, API calls).

Never put account ids, profile names, internal tool names or environment-specific setup files into the skill, briefs,
shard files or findings. Evidence is redacted at write time; prompts are not.

## Golden rules

Each rule is backed by an observed failure; the citation is where the evidence lives.

1. **Disposable account, generic intake.** Destructive, expensive, quota-consuming experiments are the default - because
   wave 1 alone left 7-day KMS deletions and an undeletable system backup (METHOD-LOG 2026-10-09, wave 1).
2. **Blindness.** Hypothesizers, probers and explorers never read `CONTROLLER_DIR`, `ground-truth.yaml` or
   `candidates.md`; only catalogers and scorers do - because recall is only meaningful blind, and blind runners
   rediscovered then extended the hooks catalog (METHOD-REVIEW §2.1, METHOD-LOG 2026-10-09 wave 1).
3. **Hypothesis generation is never count-capped.** Generate -> `semantics coverage` -> gap-fill "until every gap is covered
   or explicitly dismissed" -> re-measure - because 3 of 4 analysts stopped exactly at the cap with 63% doc-sentinel
   coverage; the gap-fill pass added 157 hypotheses cited by 97 findings (METHOD-LOG 2026-10-08, METHOD-REVIEW §2.2).
   Allow a few targeted public-doc fetches; doc-vs-knowledge contradictions are high-value hypotheses.
4. **Sub-agent sizing.** One coherent area per agent, <= ~40 KB of input, <= ~50 structured outputs; write the output file
   first and append in batches; an agent that produced no file within its budget is re-launched with a narrower brief,
   never re-sent - because every 3-area brief and the 75 KB scoring digest failed silently; 39/34 KB halves succeeded
   (METHOD-LOG 2026-10-08, 2026-10-09 wave 2; METHOD-REVIEW §4).
5. **The file store is the truth.** `status.json`, `findings.draft.yaml`, `scoring/matches-*.yaml`, decision files - never
   the agent's reply - because a runner's final report was content-filtered after its work was done; `semantics finding
   import-all` recovered 15 drafts (METHOD-LOG 2026-10-09 wave 2). `test -f` every path a prompt names before launching
   (a glob deleted the shared brief and silently broke every runner - METHOD-LOG 2026-10-09 wave 1).
6. **Shared-account hygiene.** `lab.name()` + `lab.register()` for everything created; `lab.lock()` for account-level
   serialization; per-runner process naming, never a generic `pkill`; sub-resource Describe polling <= 1/s; probes
   delete their own resources; runners never edit files outside their own probe directories; `semantics sweep` at the end -
   because one runner's `pkill -f probe.py` killed another's probe and one runner sed-edited siblings' files
   (METHOD-LOG 2026-10-09 wave 1).
7. **Probe clients have no retries** (`total_max_attempts: 1`); sweeps and setup steps may retry - because `max_attempts: 2`
   hid ~40% of first-attempt throttles (METHOD-LOG 2026-10-09 wave 1, METHOD-REVIEW §4).
8. **Record refutations and ranges.** Refuted hypotheses are findings (`status: refuted`); every duration carries
   `measurements` with `n` - because the same operation measured 2 s and 409 s, 13-75 min, 81-766 s (METHOD-LOG
   2026-10-09, METHOD-REVIEW §6). Docs quote ranges; e2e waits are status-driven.
9. **Mandatory phases, in order** (next section) - because the creative round was skipped in the first execution and, when
   forced, found controller traps nothing else finds; cheap/dense families first also calibrate timings for the expensive
   ones (METHOD-REVIEW §2.3, §2.5).
10. **Ground truth is itself a hypothesis set.** Score evidence against it and it against evidence; emit
    `scoring/ground-truth-corrections.md`; surface confirmed suspects as "Handling gaps" - because 24% of the frozen
    hooks-derived beliefs were stale or wrong (METHOD-REVIEW §2.1, METHOD-LOG 2026-10-09 wave 2).
11. **Externalize operator memory.** Rewrite `services/<svc>/STATUS.md` and run `semantics manifest update <svc>` at every phase
    boundary; read digests, never raw evidence; fan out whenever work is independent - because one 350 KB artifact stalled
    agents and the operator's own context is the scarcest resource (METHOD-LOG 2026-10-08).
12. **Rendered docs are generated.** Hand-written content lives in preserved blocks or `docs/api-semantics/supplementary/`;
    no controller README edits; `AGENTS.md` pointer only (`critical:` lines only for a truly exceptional service); all
    findings are documented (low-impact in appendices, long notes in `details/`) - per `templates/RENDER-SPEC.md` and the
    pilot's recorded decisions (`services/dynamodb/STATUS.md`).

## Phases

Numbering and names are those of `workflows/investigate-api-semantics.md`, which holds the operator steps, inputs/outputs,
parallelism and failure handling per phase; this section is the command sheet. Agent kinds are the SOPs in
`roles/semantics-*.md`. Where a step has no `semantics` command, it says so. Two checkpoints with the user: after scoring
(Phase 5) and before rendering (end of Phase 8).

### Phase 0: Intake and lab setup

```bash
cd /path/to/aws-api-semantics
uv venv .venv && . .venv/bin/activate && uv pip install boto3 pyyaml jsonschema
export AWS_API_SEMANTICS_LAB="$PWD" AWS_API_SEMANTICS_PROFILE="<profile>"
export AWS_API_SEMANTICS_PRIMARY_REGION="<r1>" AWS_API_SEMANTICS_SECONDARY_REGION="<r2>"
semantics() { python "$AWS_API_SEMANTICS_LAB/cli/semantics.py" "$@"; }
semantics init-service <svc> --prefix <PFX> --controller-repo aws-controllers-k8s/<svc>-controller \
  [--controller-dir CONTROLLER_DIR] --regions <r1> <r2>      # manifest.yaml, STATUS.md, probes/ findings/ static/ locks/
                                                              # skip when services/<svc>/ exists: read STATUS.md, fix
                                                              #   manifest.regions by hand, resume at the recorded stage
semantics vocab                                               # the vocabulary loads
grep -n "<svc>" harness/deleters.py                           # DISCOVERERS + SPECIAL_DELETERS entry for the service?
semantics sweep <svc> --dry-run                               # must list a lab-prefixed throwaway resource you created
```

`manifest.yaml` gets the model versions (`go.mod`, `ack-generate-metadata.yaml`) and controller commit; the intake
answers go into STATUS.md. **Sweep support is a Phase 0 deliverable**: `harness/deleters.py` needs a discoverer (lists
lab-prefixed resources of the service) and, for parent/child hierarchies, a special deleter that empties the parent, for the
service and for every sibling service probes will touch (KMS keys, S3 buckets, IAM roles); verify it by creating one
lab-prefixed resource tree outside the registry and watching `semantics sweep <svc>` remove it. Check the service's name
patterns: when they reject `-`, `lab.name(x, sep="_")` exists and the convention goes into every shard header.
Keep the operator environment in a file outside every repo (profile, regions, `AWS_API_SEMANTICS_LAB`, venv `PATH`, `semantics` function); prompts to
sub-agents name that file's path so they can `source` it - never its contents. Recommended: a smoke probe
(`<resource>/round-trip/smoke`: create, describe, delete, one finding) that runs, imports and sweeps clean - it doubles as
the probers' working example. Exit: `semantics digest <svc>` runs; sweep discovers and deletes the service's resources; the
user has confirmed the account is disposable.

### Phase 1: Ground-truth freeze (skip when CONTROLLER_DIR is `none`)

Catalogue what the controller believes and handles so the investigation is measurable; the catalog is itself a
hypothesis set (METHOD-REVIEW §2.1). Delegate **catalogers** (`roles/semantics-cataloger.md`): one per resource or coherent
hooks area with disjoint id ranges, each writing a fragment `services/<svc>/ground-truth.<area>.yaml` (one 9-resource
cataloger produced nothing; "ReplicationGroup" vs "everything else" worked - METHOD-LOG 2026-10-08).

```bash
# no command: concatenate the fragments (plain YAML lists) into services/<svc>/ground-truth.yaml with one header comment
semantics gt validate <svc>
# no command: candidates.md from the `suspect: true` entries; ground_truth_frozen_at: <commit> in manifest.yaml
```

Exit: 0 errors; every `generator.yaml` resource has entries; `candidates.md` exists. From here on nothing from the
controller or the catalog goes into a shard or brief.

### Phase 2: Static analysis and hypotheses (coverage-driven)

The backbone: 93% of structured findings and 28 of 30 novel-high findings cited a hypothesis (METHOD-REVIEW §2.2).

```bash
semantics static <svc> [--controller-dir CONTROLLER_DIR] # static/: model.json, operations/resources/field-matrix/enums/errors/
                                                        #   shape-pairs/codegen-hints .json, doc-sentinels.md, summary.md
# no command: write static/areas.yaml {area: {nouns: [...], ops: [...]}} - 3-6 areas, one resource or coherent API family each
semantics slices <svc> --areas services/<svc>/static/areas.yaml # static/slices/<area>.md; wc -c, split any over ~40 KB
# write services/<svc>/hypotheses-plan.yaml: ordered sources list fragment paths relative to that plan
semantics hypotheses <svc>                                   # generated hypotheses.yaml; optional hypotheses.md via markdown: {}
semantics coverage <svc> --areas services/<svc>/static/areas.yaml # coverage.md + coverage.json: uncovered operations,
                                                                #   op x family cells, fields, enum values, errors, sentinels
```

Delegate **hypothesizers** (`roles/semantics-hypothesizer.md`; items per `roles/schemas/semantics-hypothesis-item.md`): pass 1
one per area with its slice as input and no count target, ever; pass 2 gap-fill per area from the uncovered lists
("stop only when every item is covered or explicitly dismissed") into `hypotheses.<area>.pass-2.yaml`. Add each fragment
to the ordered `sources` in `services/<svc>/hypotheses-plan.yaml`; retain all existing ids and reject duplicates.
Run `semantics hypotheses <svc> [--plan <path>]`, then coverage after each pass, until the uncovered list is boilerplate.
One hypothesizer in `claims` mode reads `static/doc-sentinels.md` -> `creative/seed-doc-claims.md` for Phase 4. Exit:
100% of operations, status enums and error shapes covered; sentinel coverage no longer rising (pilot: 63% -> 84%).
Operator reads `coverage.md` Summary only.

Two model sources: the lab probes the installed botocore model; the controller is generated from the
`aws-sdk-go-v2` module in its `go.mod` (manifest `model.aws_sdk_go_v2_module`), usually older. Compare
`static/operations.json` with the controller's `generator.yaml` / `apis/*/generator.yaml` operation set (the
`--controller-dir` run writes `codegen-hints.json` `controller` section) and list the operations and members the
controller cannot see in STATUS.md. Hypothesizers stay blind and cover them anyway; the scorer and the render treat
findings about them as scope / "needs SDK bump" items, not as controller misses.

### Phase 3: Structured probe shards

72% of findings and 94% of ground-truth matches (METHOD-REVIEW §2.3). Write `services/<svc>/shards/plan.yaml` with
`header`, `max_kb: 40`, and ordered `shards` entries (`title`, `wave`, `select`, optional `exclude`/`notes`). Select by
`area`, `probe_family` and `est_cost`; `select.pass` selects a hypothesis pass. Aim for 15-30 hypotheses per shard.
The header carries regions, lock names (`<svc>:<constraint>`), polling limits and `harness/GUIDE.md`.
Run `semantics shards <svc> --plan services/<svc>/shards/plan.yaml` to generate `<ID>[a|b|...].md` and `assignment.json`.
The first matching shard wins; dismissed items are excluded and unmatched items are reported. Adjust the plan and
regenerate when membership or size needs changing; `part_sizes` can set exact split counts.
Wave 1 = cheap/dense families; background wave = state-machine, cross-region, consistency-windows, limits, soaks (order
and yields: `references/probe-families.md`).

Delegate **probers** (`roles/semantics-prober.md`, mode `shard`, report `roles/schemas/semantics-prober-report.md`): one per
shard, 4-7 live at once; `test -f` the shard and GUIDE first. Each prober scaffolds, runs and imports:

```bash
semantics probe new <svc> <resource>/<family>/<variant> --purpose "..." --hypothesis H-X-001 ... [--exclusive <svc>:<constraint>] [--est 600] [--irreversible]
nohup python services/<svc>/probes/<resource>/<family>/<variant>/probe.py > .../run.log 2>&1 &
semantics finding import <svc> <resource>/<family>/<variant>  # validates, coerces near-misses, assigns ids
```

Operator after every wave, whatever the replies said:

```bash
semantics probe status <svc>; semantics finding import-all <svc>; semantics finding validate <svc>
semantics probe resume-paused --all                            # after a credential refresh
semantics digest <svc>; semantics manifest update <svc>
semantics sweep <svc> --dry-run && semantics sweep <svc>        # leftovers must be running probes or findings themselves
```

Append the reports' "Surprises" to `services/<svc>/creative/seed-surprises.md`. Exit: every shard `completed` or listed
in STATUS.md as background with probe ids; `drafts_pending: 0`; sweep clean except documented leftovers.

### Phase 4: Creative round and doc-claims audit (parallel)

Lower density (0.36 vs 1.05 findings/100 calls) but controller traps and the per-code error-message catalogue nothing
else finds; 27% of testable documentation claims were wrong or imprecise (METHOD-REVIEW §2.5, §2.8). Mandatory,
time-boxed.

```bash
semantics creative seeds <svc> --claims-per-list 35 # existing-titles.txt, seed-error-messages.md, seed-doc-claims-<n>.md
# author seed-naive-controller.md and seed-cross-service.md; seed-surprises.md comes from probe reports
```

The command reads findings, recorded evidence and the authored `creative/seed-doc-claims.md`. Check its size report;
give agents <= 40 KB slices and lower `--claims-per-list` when needed. Regenerate outputs from their sources.

Delegate 3-4 **explorers** (`roles/semantics-explorer.md`), one seed each, ~2 h; and 1-2 **probers** in mode `doc-claims`.
Probes land under `<resource>/creative/<variant>` and `service/static/doc-claims-<n>`; findings are tagged
`[creative, <seed>]` or `[doc-claim, C0xx]` (`semantics consolidate` later sets TRUE/UNTESTABLE verdicts to impact low).
Then the Phase 3 after-wave block. Exit: every seed has a report or a narrower re-launch; every claim has a
TRUE/FALSE/PARTLY/UNTESTABLE verdict finding.

### Phase 5: Scoring (skip when there is no ground truth)

Recall, novelty ratings, suspect verdicts and the follow-up list (METHOD-REVIEW §2.6).

```bash
# no command: write scoring/areas.yaml {area: {resources: [...], gt_filter, gt_exclude, finding_filter, finding_exclude}} (regexes)
semantics score digests <svc> --areas services/<svc>/scoring/areas.yaml # scoring/digest-<area>.md; prints bytes - split any > 40 KB
semantics score merge <svc>     # scorecard.md + scoring/merged.json; unscored entries count as missed
semantics score apply <svc>     # ground_truth_ids; handling unhandled -> handled / partial / suspect-bug; handling_ref; notes
```

Splitting a digest over 40 KB: the size is ground-truth entries x candidate findings, so split the *area row* in
`areas.yaml`, not the file - two rows with the same `gt_filter` and complementary `finding_filter`/`finding_exclude`
(e.g. by operation family or sub-feature noun), or two rows with disjoint `gt_filter`s over the same findings. Every
ground-truth id must land in at least one digest (`semantics score merge` reports unscored entries as missed). The pilot
ran 63-79 KB digests in 4 of 7 areas and lost one scorer to it.

Delegate **scorers** (`roles/semantics-scorer.md`, output `roles/schemas/semantics-scorer-output.md`): one per digest ->
`scoring/matches-<area>.yaml`. Write an authored blind brief `shards/F-followups.md` from the `probe:` sketches of
every miss/partial and the unresolved suspects.

**Checkpoint 1 (user)**: recall by discoverability, misses with their planned follow-ups, suspect verdicts (confirmed
bugs = the controller's issue list), API calls and hours vs budget. Ask: approve the follow-ups, drop anything,
continue. Record the decision in STATUS.md.

Exit: every ground-truth entry has exactly one verdict; every miss has a probe sketch; decision recorded.

### Phase 6: Scorer-driven follow-ups

Delegate 1-3 **probers** in mode `follow-up` over `shards/F-followups*.md` (pilot: 9 probes, 4.3k calls, recall 96% ->
97%, 100% of observable entries, 3 suspects settled). Then import-all; write `scoring/matches-followups.yaml` (same
schema), reconcile superseded notes/verdicts in the authored match files, then `semantics score merge <svc>` and
`semantics score apply <svc>`; sweep. Merging follows the verdict ranks in the scorer output schema.
Exit: every miss is `found`/`partial` or noted "not observable: <why>"; every suspect is `confirmed-bug`,
`refuted` or `unresolved` with a reason.

### Phase 7: Consolidation

6% literal duplicates, 41 contradictions (mostly one-cell over-generalizations), 45 title fixes in the pilot
(METHOD-REVIEW §2.7). Write `consolidation/areas.yaml`: ordered areas with `resources`, `finding_filter`,
`finding_exclude` and optional `rest: true`. Keep related behaviors together; each finding goes to the first matching
area. Run `semantics consolidate digests <svc> --areas services/<svc>/consolidation/areas.yaml --max-bytes 40000`.
It generates `consolidation/digest-<area>[-a|-b|...].md` plus `assignment.json`, with behavior excerpts and relation ids.
Check reported sizes and unplaced findings; adjust the areas or byte limit and regenerate.
Delegate **consolidators** (`roles/semantics-consolidator.md`, output `roles/schemas/semantics-consolidation-output.md`)
one per generated digest -> `consolidation/decisions-<area>.yaml` (include the split suffix); they never edit findings.

```bash
semantics consolidate <svc>     # applies decisions-*.yaml: duplicate_of, related, contradiction notes, titles, doc-claim impact
semantics finding validate <svc>
```

Contradictions resolved "re-probe" go into `shards/F-followups-2.md` and run with Phase 8. Exit: decisions applied; 0
validation errors; no contradiction without a resolution or a queued probe.

### Phase 8: Second-opinion sample and ground-truth corrections

Error rate of recorded behavior (pilot: 20/20 confirmed; the real defect class is over-generalized titles -
METHOD-REVIEW §5.1) and the list of controller beliefs the evidence overturned.

```bash
semantics reverify sample <svc> --fraction 0.15 --per-set 5 --seed 7
```

Eligibility is implicit: confirmed, high-impact canonical findings with exactly one evidence probe, excluding doc-claim
and static findings, and no corroboration from a different probe with the same category and operation set. Sampling
is biased to cheap re-runs and stratified by resource. The generated `consolidation/reverify-sample.md` carries title,
behavior, repro, measurements and operations; `reverify-sample.json` carries probe ids and is operator-only.
Delegate **probers** one Markdown set each in mode `reverify`, forbidden to open the original probe directories;
probes under `<resource>/creative/reverify-set-<x>`; verdicts CONFIRMED / CORRECTED / REFUTED / UNTESTABLE.

```bash
semantics finding show <svc> <id>                                             # read tags/notes first: update replaces whole fields
semantics finding update <svc> <id> tags='[<existing tags>, reverified]' --touch # CONFIRMED (verdict appended to notes); --touch last
semantics finding update <svc> <id> behavior='...' title='...' --touch          # CORRECTED (old text kept in notes)
semantics finding update <svc> <id> status=refuted notes='...'                  # REFUTED
```

Run `semantics gt corrections <svc>` to generate `scoring/ground-truth-corrections.md` from current
`scoring/merged.json`: match notes containing `CONTRADICTED:`, `STALE:` or `OVERGENERALIZED:`, plus suspects with
`verdict: confirmed-bug`. If evidence changes a scoring conclusion, edit the authoritative `scoring/matches-*.yaml`
notes/verdicts, run `semantics score merge <svc>` and `semantics score apply <svc>`, then regenerate the report.
`ground-truth.yaml` stays as frozen: it records what the controller believes.

**Checkpoint 2 (user, before rendering)**: sample results; corrections list; proposed `render.yaml` partition; confirm
the defaults - all findings documented (low-impact in appendices, long notes in `details/`), suspect bugs rendered as
"Handling gaps", no controller README changes, `AGENTS.md` pointer only (`critical:` lines only for a truly
exceptional service).

Exit: sample verdicts recorded (a REFUTED result re-checks its `related` siblings); corrections list written; render
decisions in STATUS.md.

### Phase 9: Render and close-out

```bash
# no command: write services/<svc>/render.yaml per templates/RENDER-SPEC.md - docs partition (file, title, resources,
#   include/exclude, description), notes_policy (drop_paragraph_prefixes, inline_excerpt_chars), size_warn_lines
#   (pilot: 1500), seed_aliases, critical
semantics render <svc> --controller-dir CONTROLLER_DIR --dry-run # assignment counts, sizes, unassigned-finding warnings
semantics render <svc> --controller-dir CONTROLLER_DIR           # docs/api-semantics/{README,index,service,<doc>}.md, details/, AGENTS.md
git -C CONTROLLER_DIR status --short                            # only docs/api-semantics/, AGENTS.md (+ CLAUDE.md if new)
semantics phases <svc>                                         # phase-analysis.md: yield per family / shard / hypothesis pass
semantics manifest update <svc>; semantics sweep <svc> --dry-run && semantics sweep <svc>
```

Delegate **doc-writers** (`roles/semantics-doc-writer.md`): task A before the first render - one per doc stem, input the
stem's findings (<= 40 KB) -> `services/<svc>/supplementary/<stem>.overview.md` (+ `.open-questions.md`); task B after
it - review the rendered docs (MUST FIX / SHOULD FIX, each pointing at a finding, a `render.yaml` key or a seed, never
at the rendered file). Iterate the partition until no doc is over budget or the overflow is accepted; never hand-edit
generated sections. Close out: rewrite STATUS.md (stage, numbers, decisions, account state incl. mandatory-retention
leftovers, open experiments); append a dated entry to the lab's `METHOD-LOG.md`; commit the lab; propose (do not open)
the controller branch/PR. Exit: render clean or warnings acknowledged in STATUS.md; review has no MUST FIX; controller
`git status` shows only `docs/api-semantics/` and `AGENTS.md` (+ `CLAUDE.md`); `CONTROLLER_DIR/README.md` untouched.

## Delegation guidance

- **Kinds of work, not fixed slots**: cataloger, hypothesizer (pass 1, pass 2, `claims`), prober (modes `shard`,
  `follow-up`, `doc-claims`, `reverify`), explorer, scorer, consolidator, doc-writer (tasks A, B). Launch as many of a
  kind as there are independent areas; never give one agent two kinds.
- **Fan out** per area (hypotheses), per shard (probes, 4-7 live against one account), per seed (creative), per digest
  (scoring, consolidation), per doc stem (doc-writers); expensive shards run in the background while cheap ones return.
- **Reports are for the operator's digest, not for state**: <= 60 lines (probers), <= 40 (explorers, doc-writers),
  <= 20 (hypothesizers, consolidators), <= 15 (catalogers, scorers).
- **No file within budget -> re-launch with half the scope** (fewer hypotheses, one resource, half the digest). Content
  filtering is non-deterministic - the same wording succeeded on retry; do not debug the prompt (METHOD-LOG 2026-10-09
  wave 3).
- **Independence as a corrective**: two runners on adjacent territory beat one runner with a bigger brief; the second
  catches the first's over-generalizations (METHOD-REVIEW §4, §5.1).
- **Blindness boundary**: only catalogers, scorers and doc-writers (for handling text) may open `CONTROLLER_DIR` or
  `ground-truth.yaml`. Say so in every other brief.
- **Generic sub-agents** (no named `semantics-*` agents available, e.g. OpenCode `general`, Kiro): every prompt carries
  the role file path, the schema path, the lab path, the env file path to `source` first (the file lives outside every
  repo; the prompt names the path, never the profile), the mode, the input paths and the output path, plus the two
  sentences "write the output file first, append in batches" and "you are BLIND: do not open CONTROLLER_DIR,
  ground-truth.yaml, candidates.md, scoring/" where the role requires it. Paths, never contents.

## Context management for the operator

- `services/<svc>/STATUS.md` is the memory: stage, next step, numbers, decisions taken with the user, account state,
  running, blockers. Rewrite it at every phase boundary; read it first when resuming. `manifest.yaml`
  (`semantics manifest update`) holds model versions, controller commit, `ground_truth_frozen_at`, counts.
- Read digests only: `semantics digest <svc>`, `semantics probe status <svc>`, `coverage.md` Summary, `scorecard.md` Recall/Missed,
  consolidation counts, the render size report, agents' bounded reports; one finding via `semantics finding show <svc> <id>`.
- Never load `evidence.jsonl`, `registry.jsonl`, whole `findings/*.yaml`, `hypotheses.yaml` (pilot: 410 KB),
  `field-matrix.json` (350 KB) or full scoring digests into the operator context; give agents slices instead.

## Budget expectations (DynamoDB pilot)

| item | pilot value |
|---|---|
| probes | 125 (12 structured shards in 2 waves, 9 scorer follow-ups, 32 creative, 4 doc-claims) + 20-finding re-verification sample |
| API calls | ~62,600 (structured ~37.6k, creative ~14.5k, follow-ups 4.3k, doc-claims 1.5k, re-verify 1.1k) |
| hypotheses | 365 live + 18 dismissals (pass 1: 208, gap-fill pass 2: 157) |
| findings | 548 recorded, 515 canonical, 253 high-impact; 45 refuted hypotheses; 12 confirmed controller bugs |
| ground truth | 94 entries for DynamoDB (the pilot's 6 catalogers covered four services); 97% found-or-partial, 100% of observable entries; 23 corrections |
| agents | ~6 catalogers, 4 + 4 hypothesizers, 5 + 7 probers, 2 follow-up probers, 4 explorers x ~2 h, 2 auditors, 8 scorers, 6 consolidators, 4 re-verifiers |
| operator time | ~1.5 operator-days with parallel agents; wall-clock dominated by state-machine / cross-region / soak probes |
| leftovers | 7-day KMS pending deletions, undeletable system backups (findings themselves) |

Scale by operations x families: a service with a third of DynamoDB's control-plane operations needs roughly a third of
the hypotheses and shards; expensive families scale with the number of asynchronous resources, not operations. Budget
long consistency-window polls and burst "limits" probes explicitly - they were the lowest yield per call
(METHOD-REVIEW §3).

## Modes

- **Full**: Phases 0-9 for a service with no findings yet. Without a controller, skip Phase 1 and Phase 5; everything is
  then `handling: unhandled` and the docs have no "Handling gaps".
- **Update**: Phases 0-9 on the delta for a service already in `services/<svc>/` after an SDK model bump, a new
  resource, aged findings or a controller change: re-run `semantics static`, diff the model fingerprint and `static/*.json`
  against the previous run, hypothesize and probe the delta, re-verify aged/contradicted/shape-touching findings,
  re-derive ground truth from the current controller commit, consolidate, re-render (preserved blocks survive). Steps
  and the CLI gaps: [update-mode.md](references/update-mode.md).
- **Verify**: Phases 0, 3, 7 (mini), 9 for one suspected behavior: one hypothesis item in `shards/V-<slug>.md`, one
  prober, 1-3 probes, `semantics finding import`, link `related`/`duplicate_of` against `creative/existing-titles.txt`,
  re-render only if a doc changes, sweep. Same blindness and hygiene rules; no scoring. Also in `references/update-mode.md`.

### Offline snapshot regeneration

For published snapshots, `semantics static <svc> --sentinels-only` regenerates doc sentinels from the local botocore
model after checking its recorded fingerprint; install the snapshot's compatible boto3/botocore pins together with
`uv pip install "boto3==<boto3-version>" "botocore==<botocore-version>" pyyaml jsonschema` and run `uv pip check`.
`semantics score replay <svc>` and `semantics gt corrections <svc> --recorded` validate and replay the published
policies, selections and content digests in `scoring/report-inputs.yaml`. Live investigations use full `semantics static`,
`semantics score merge` and default `semantics gt corrections`; recorded replay is only for offline snapshots.
