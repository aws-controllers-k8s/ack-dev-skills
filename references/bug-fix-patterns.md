# Common Bug Fix Patterns

> **NEVER modify generated files directly.** All files marked `// Code generated by ack-generate. DO NOT EDIT.` (including `sdk.go`, `delta.go`, `manager.go`, `resource.go`, etc.) will be overwritten on the next code generation run. Fix bugs by changing `generator.yaml`, hook templates (`.go.tpl`), or `hooks.go` — then regenerate.

Reference for the most frequent root causes found in closed ACK bugs. When investigating a new bug, match the symptom to a pattern below for the likely fix approach.

## Pattern 1: Infinite Reconcile Due to JSON/Whitespace/Ordering Differences

**Symptoms:** Controller constantly reconciles detecting diffs on the same field. Diff shows the same semantic value with different formatting (whitespace, key ordering, redundant fields). Common with IAM policy documents, JSON strings, and list fields.

**Root Cause:** AWS API returns a normalized/reformatted version of a field that differs textually but is semantically identical.

**Fix:**
- **IAM policy fields:** Add `is_iam_policy: true` in `generator.yaml` → triggers `IAMPolicyDocumentEqual` comparator
- **Unordered lists:** `compare.is_ignored: true` + `delta_pre_compare` hook with custom normalization
- **Server-added defaults:** `late_initialize: {}` on those fields

**Example (sns-controller PR #111):**
```yaml
Policy:
  is_iam_policy: true
```

## Pattern 2a: Field Ignored in Delta but Missing Custom Compare Hook

**Symptoms:** User changes a field value, but no update is propagated. Controller logs show no delta detected. Resource stays synced.

**Root Cause:** Field is `compare.is_ignored: true` but the corresponding manual comparison in `delta_pre_compare` hook was never added or has a typo.

**Fix:**
1. Find `customPreCompare` in `hooks.go` or template
2. Add the missing field comparison using `ackcompare.HasNilDifference` + value equality

**Example:**
```go
if ackcompare.HasNilDifference(a.ko.Spec.AllocatedStorage, b.ko.Spec.AllocatedStorage) {
    delta.Add("Spec.AllocatedStorage", a.ko.Spec.AllocatedStorage, b.ko.Spec.AllocatedStorage)
} else if a.ko.Spec.AllocatedStorage != nil && b.ko.Spec.AllocatedStorage != nil {
    if *a.ko.Spec.AllocatedStorage != *b.ko.Spec.AllocatedStorage {
        delta.Add("Spec.AllocatedStorage", a.ko.Spec.AllocatedStorage, b.ko.Spec.AllocatedStorage)
    }
}
```

## Pattern 2b: Field Not Round-Tripped by the Read Operation

**Symptoms:** Either a perpetual delta (update fires every resync), or the user's declared value is erased from the CR after create, or an edit never propagates because it compares equal.

**Root Cause:** Read output omits the field or returns it under a different path, so code-gen cannot set it.

**Fix, in order of preference:**
1. **Recover the observed value** in `sdk_read_many_post_set_output` / `sdk_read_one_post_set_output` when Read returns it elsewhere (e.g. a Spec field `Policy` that Describe reports under `Settings.Policy`). Only when the user declared the field — otherwise an AWS default manufactures a delta.
2. **Restore from desired** only for write-only (secret refs) and create-only immutable members. Never restore a member that appears in an Update shape — it masks drift. Never restore a whole nested struct when only one member is write-only.
3. `compare.is_ignored` last. No field may be both compare-ignored and mutable.

Check whether `set` config or an existing hook already covers it before adding one.

## Pattern 3: Unchanged Field Sent in Update Causes API Error

**Symptoms:** Modifying any field triggers a terminal error about a *different* field. Error like "Modification of X is not supported" even though X wasn't changed.

**Root Cause:** Generated `sdkUpdate` builds input from all spec fields. Some AWS APIs reject update calls if certain fields are included even when unchanged.

**Fix:** Add `sdk_update_post_build_request` hook to nil out the field when not in delta:
```go
if !delta.DifferentAt("Spec.FieldName") {
    input.FieldName = nil
}
```
Or mark with `is_immutable: true` if the field truly cannot change after creation.

## Pattern 4: Nil Pointer Panic in Hook Code

**Symptoms:** Controller panics with `invalid memory address or nil pointer dereference`. Resource created in AWS but status never updates. Triggered by optional fields that are nil in certain states.

**Root Cause:** Custom hook dereferences a pointer without nil-check. AWS responses have nested optional structs where inner fields are nil when a feature is disabled.

**Fix:** Add nil checks before every pointer dereference in the chain. Convert invalid input to a terminal error rather than panicking.

## Pattern 5: ReadMany Returns Wrong Resource (Missing Filter)

**Symptoms:** Creating a resource gives "Resource already exists". Multiple CRs point to the same AWS resource. Controller adopts unrelated resources.

**Root Cause:** Generated `sdkFind` uses a List API without filtering by the specific resource's identifier.

**Fix:** Add `list_operation.match_fields` in `generator.yaml`:
```yaml
list_operation:
  match_fields:
    - ServiceId
```
Or add `sdk_read_many_post_build_request` hook to set filter parameters.

## Pattern 6: Tags Not Updating After Creation

**Symptoms:** Tags set correctly on creation but updates to tags in CR spec have no effect.

**Root Cause:** Missing/broken `syncTags` hook, or tag update API requires separate calls (AddTags/RemoveTags) not wired in update path. Common bug: ARN and tag list parameters swapped.

**Fix:** Implement or fix `ensure_tags` hook that calls the correct tag API with correct parameter order. Verify the tag diff logic computes add/remove sets correctly.

**Traps that leave `Synced=True` while tags are wrong:**
- **Double-swapped arguments.** Generated code or a hook template may call `rm.syncTags(ctx, latest, desired)` while `syncTags` is declared `(ctx, desired, latest)` and swaps them again into the helper. The two swaps cancel. "Fixing" only one of them inverts the sync, so desired tags are removed on every reconcile. Trace from the generated caller (`git grep -A4 'rm.syncTags('`) through the wrapper to the helper's parameter names.
- **Dead tags-only guard.** In `if delta.DifferentAt("Spec.Tags") { ...syncTags... } else if !delta.DifferentExcept("Spec.Tags") { return desired, nil }`, the `else if` only fires on an empty delta, and the update is never called with one. A tags-only change, including the `services.k8s.aws/controller-version` tag that changes on every upgrade, syncs tags and also sends the full update. Make the guard its own `if` after the sync, as in Configuring Tags Support in the [ack-dev skill](../skills/ack-dev/SKILL.md).
- **Tags never read.** If Describe doesn't return tags and no read hook fetches them, `latest.ko.Spec.Tags` is a copy of desired. A `Spec.Tags` delta never appears, so the sync never runs. See "Tag reading" in the [ack-dev skill](../skills/ack-dev/SKILL.md).
- **The update output wipes tags.** When one Put API serves as both Create and Update and tags go through `TagResource`, the generated Update output setter sets `Spec.Tags` to nil when the response carries no tags. The runtime patches that onto the CR, and the next reconcile untags AWS. Add `set: [{method: Update, ignore: "all"}]` on `Tags`.

## Pattern 7: Adoption Fails with "Resource Not Found"

**Symptoms:** Resource adoption via annotation fails. "Adopted resource not found" or fields not populated after adoption.

**Root Cause:** Resource's primary identifier for ReadOne doesn't match what adoption provides. Or `sdkFind` checks a status field that was never set during adoption.

**Fix:**
- Set `is_arn_primary_key: true` if identified by ARN
- Guard status-field checks with nil: `if ko.Status.ID != nil { ... }`
- Verify adoption populates all fields needed for ReadOne

## Pattern 8: Deletion Succeeds in K8s but AWS Resource Persists

**Symptoms:** CR deleted (finalizer removed) but AWS resource still exists. Batch delete APIs return 200 with errors in response body.

**Root Cause:** Some AWS delete APIs return success HTTP 200 with an `Unsuccessful` array that the generated handler doesn't inspect.

**Fix:** Add `sdk_delete_post_request` hook that checks response for error entries and returns an error to prevent finalizer removal.

## Pattern 9: Immutable Field Change Creates Orphaned Resource

**Symptoms:** Changing a primary identifier field (e.g., `spec.name`) creates a new AWS resource. Old resource becomes orphaned.

**Root Cause:** Identifier field not marked immutable. Controller treats it as new creation.

**Fix:** Mark identifier fields with `is_immutable: true` in `generator.yaml`.

## Pattern 10: Custom Update Completely Non-Functional

**Symptoms:** Controller logs "updated resource" but AWS state never changes. `custom_method_name` specified but implementation has logic errors.

**Root Cause:** Custom update implementations use `diff.Path.Contains()` incorrectly (prefix matching, not substring) or compute add/remove sets wrong.

**Fix:** Replace broken `custom_method_name` with generated update + hooks (`sdk_update_pre_build_request`/`sdk_update_post_build_request`). Add `synced.when` for async resources.

## Pattern 11: Update Rejected Because Resource Is in a Transitional State

**Symptoms:** An update succeeds but the resource goes terminal shortly after with an error like "You can't update X in UPDATING state" / "resource is not in a modifiable state". Often only reproduces on the *second* reconcile: the first update is accepted, the resource enters a transitional state (e.g. UPDATING), and the controller immediately attempts another update before it returns to ACTIVE. Common with async update APIs whose Describe keeps returning the pre-update values until the change propagates (so the delta keeps firing).

**Root Cause:** Generated `sdkUpdate` has no guard on the resource's current status. AWS updates are asynchronous (ACTIVE → UPDATING → ACTIVE) and reject any update issued while not ACTIVE.

**First confirm the API actually rejects it.** Many async APIs accept unrelated updates mid-flight and reject a re-sent in-flight change with a retryable error; a guard there only makes the controller stricter than the API. Verify against a real resource when docs are vague.

**Fix (preferred — declarative):** Add an `updateable.when` guard. Code-gen emits a status check at the top of `sdkUpdate` that returns `ackrequeue.NeededAfter` (transient, NOT terminal) when the status is not in the allowed set, so no update is attempted mid-flight:
```yaml
updateable:
  when:
    - path: Status.Status
      in: [ACTIVE]
  requeue_after_seconds: 30   # optional, default 30
```
There is a matching `deletable.when` for delete-state guards. `updateable.when` is **not emitted** when `update_operation.custom_method_name` is set — the guard must live in the custom method.

**Fix (fallback — custom):** Only if the guard needs logic beyond a status-in-list check, add a `sdk_update_pre_build_request` hook that returns a requeue.

> Prefer `updateable.when` over a hand-written `sdk_update_pre_build_request` requeue helper — the generated guard is identical and needs no `hooks.go` code or unit test.

## Pattern 12: Late Initialization Does Not Take Effect

**Symptoms:** A field has `late_initialize`, but the spec never gets the AWS value and the same nil-vs-value delta comes back on every reconcile. Or, right after an upgrade, every existing CR sends one update.

**How it runs:** In `Sync`, `lateInitializeResource` runs after `updateResource`, and only if the update succeeded. It fills fields that are nil on the object the update step returned, then patches the CR with the difference.

**Root causes:**
- **The update fails every time** (Pattern 13), so late-init is never reached.
- **The difference is suppressed** (compare-ignored, or dropped in a compare hook). With an empty delta, `updateResource` returns the ReadOne result, which already holds the observed value. Late-init has nothing to fill, and existing CRs keep the field unset. New CRs still get it at create. That is fine when unset means "leave as is". Otherwise, let the generated compare see the difference: the first reconcile sends one update, then late-init fills the spec.
- **A sibling field has the same default.** Read every server-defaulted field from a CR that sets only the required fields, including defaults that appear only when a feature is enabled, and late-initialize all of them.
- **The service returns a value it won't accept back**, such as `""` where Update requires a minimum length. Late-init copies it, and the next update fails. Normalize it to nil in a `sdk_read_many_post_set_output` or `sdk_read_one_post_set_output` hook.

**Note in the PR:**
- After the upgrade, each existing CR sends one update with the field omitted before late-init fills it. If that update is costly (it creates a version or restarts something), drop the difference in `delta_post_compare` while the spec leaves the field unset. Existing CRs then keep the field unset, as described above.
- Out-of-band changes to a late-initialized mutable field are reverted from then on.
- Once any field is late-initialized, `LateInitialize` calls ReadOne on every reconcile, which roughly doubles read calls.

## Pattern 13: An Update That Can Never Succeed

**Symptoms:** The same update error on every reconcile, for a field the user never set: a request with no update fields, an empty list, or a valueless attribute rejected by the API. It often starts after an upgrade.

**Root Cause:** A nil-vs-default delta routes into an update whose request is built from the spec. The spec has nothing to send, so the API rejects the request. Because the update fails, late-init never runs (Pattern 12), and the delta never closes.

**Fix:** Skip the call when the desired value is nil or empty and the API rejects that, e.g. `if delta.DifferentAt("Spec.X") && len(desired.ko.Spec.X) > 0`. The update then succeeds, and late-init records the AWS value in the same reconcile. When a custom update builds a separate request per changed path, check that the request carries something before calling the API.
