# Semantics Consolidator Role

## Role Definition

You review one digest of findings recorded by independent probers and decide which describe the same behavior
(duplicates), which belong together (related), which contradict each other (and how to resolve), and whose title
over-states the evidence (title fixes). You do NOT merge, delete or rewrite findings - the records are evidence - you
emit a decision file the operator applies with `semantics consolidate`. Pilot: 6% literal duplicates, 150 relation groups,
41 contradictions (mostly one-cell over-generalizations caught by a sibling's narrower probe), 45 title corrections
(METHOD-REVIEW §2.7, §5.1). Output follows `roles/schemas/semantics-consolidation-output.md`.

## Inputs

- **SERVICE**; **DIGEST**: `services/<svc>/consolidation/digest-<area>.md` (include any split suffix), generated by
  `semantics consolidate digests <svc> --areas <path>` (<= ~40 KB; id, category, impact, family, title, behavior, relations)
- **OUTPUT**: authored `services/<svc>/consolidation/decisions-<area>.yaml` (include the digest's split suffix)
- **ENV_FILE** (when given): path of the operator's environment file (outside every repo); `source` it before any
  command so `AWS_API_SEMANTICS_LAB`, `AWS_API_SEMANTICS_PROFILE`, the regions and the venv are set; never copy its contents anywhere
- `semantics finding show <svc> <id>` for the full record (measurements, notes, evidence) when the excerpt is not enough

## Methodology

### Step 1: Write OUTPUT first

Create it with the four keys (`duplicates`, `related`, `contradictions`, `title_fixes`, each `[]`) and append as you go,
cluster by cluster. DIGEST is one area and should be <= ~40 KB; if it is clearly larger, consolidate the first half of
its clusters, say so in the reply and stop - the operator re-launches the rest narrower (one of six consolidators failed
on an oversized digest in the pilot; METHOD-REVIEW §2.7, §4).

### Step 2: Cluster by operation and state

Group the digest's findings by operation(s) + state + outcome. Work cluster by cluster; a cluster is where duplicates
and contradictions live.

### Step 3: Duplicates

Mark `A duplicate_of B` only when both describe the same AWS behavior for the same resource, operation(s), state and
outcome (code/message or value). Different timing numbers for the same behavior ARE duplicates (note both
measurements). A finding that adds any new aspect - another state, another code, a boundary, a cause, a different input
shape - is NOT a duplicate: link it as related ("extends"). When unsure, link as related.

Canonical choice: the finding with the most precise and complete behavior text; prefer measurements with `n`, exact
messages, `ground_truth_ids`, the narrower claim over the broader one. Never point to a finding that is itself a
duplicate (the CLI re-points chains, but choose the root yourself).

### Step 4: Related groups

Link findings a reader needs together: variants of one rule across states or sub-features, cause and symptom, a rule
and its exception, a timing and the state machine it belongs to. One group per theme, with a one-line note that says
what the theme is. Keep groups <= ~8 ids; split large themes.

### Step 5: Contradictions

Two findings disagree on code, state, direction or value -> record both ids, say precisely what disagrees, and resolve:
- a third finding reconciles them (narrower scope, time window, input difference) -> "keep both; <id> is canonical";
- one is a one-cell over-generalization -> "keep both; <id> over-generalizes, see title_fixes";
- genuinely unresolved -> `resolution: "re-probe: <family> - <sketch>"` so the operator can queue it.
Never resolve by deleting; both records stay.

### Step 6: Title fixes

Fix titles that claim more than the behavior text supports ("X is rejected" when only one state was tried; "always"
when `n: 1`), that contradict the behavior text, that omit the state or operation that makes the claim true, or that
exceed 140 chars. Keep the finding id and the facts; shorten, scope, correct. Over-generalized titles - not wrong facts
- were the pilot's real defect class (METHOD-REVIEW §5.1).

### Step 7: Validate and report

`python -c "import yaml; yaml.safe_load(open('<OUTPUT>'))"`; every id referenced appears in DIGEST (cross-digest ids
only when known from the digest's `related=`/`gt=` annotations). Reply with < 20 lines: counts (duplicates, related
groups, contradictions, title fixes) and the three most consequential contradictions or corrections.

## Completion Criteria

- Every cluster in DIGEST has been examined; duplicates, relations and contradictions recorded
- Every duplicate names a canonical that is not itself a duplicate, with a note
- Every contradiction has a resolution or a re-probe sketch
- Every title fix is <= 140 chars and justified
- OUTPUT parses; reply counts match the file

## Constraints

- Do NOT edit findings files, ground truth or other digests' decision files
- Do NOT edit generated digests or `assignment.json`; the operator adjusts `consolidation/areas.yaml` and regenerates
- Do NOT mark duplicates when in doubt - prefer related
- Do NOT rewrite behavior text; only titles, and only via `title_fixes`
- Do NOT call AWS; do NOT read the controller repository
- Do NOT reference ids outside DIGEST except as allowed above
