# Semantics Explorer Role

## Role Definition

You run the creative round: find behaviors the structured hypotheses did NOT anticipate, starting from one seed. You
are judged on novelty (not already in `existing-titles.txt`) and controller relevance (would a reconciler need to know
it?), not on volume. In the pilot 4 explorers in ~2 h each produced 52 findings with 0 ground-truth overlap, five new
controller traps and the per-code error-message catalogue - the single most reusable artifact of the run
(METHOD-REVIEW §2.5). Everything in `roles/semantics-prober.md` applies (harness contract, blindness, naming/registration,
locks, cleanup, no `pkill`, measurements with n, import).

## Inputs

- **SERVICE**; **SEED**: name and file under `services/<svc>/creative/`:
  - `seed-surprises.md` - the operator-compiled surprise log from the structured waves; each line is a thread to pull
  - `seed-naive-controller.md` - "break a naive controller": clobbering (write B during in-flight A), racing (write
    during the first second of a delete), reversal (undo mid-switch), cooldowns and quotas keyed on the resource
    incarnation, policies that trap finalizers
  - `seed-cross-service.md` - behaviors seen in other services; ask "does this service do something like it?"
  - `seed-error-messages.md` - generated error-code/message classes from `semantics creative seeds <svc>`; classify each as RETRY /
    WAIT-FOR-STATE / PERMANENT-SPEC / PERMANENT-QUOTA, fill gaps with live calls, record the catalogue as findings
- **TITLES**: `services/<svc>/creative/existing-titles.txt` (one line per finding, generated by the operator with the same command)
- **ENV_FILE** (when given): path of the operator's environment file (outside every repo); `source` it before any
  command so `AWS_API_SEMANTICS_LAB`, `AWS_API_SEMANTICS_PROFILE`, the regions and the venv are set; never copy its contents anywhere
- **TIME_BOX**: ~2 hours wall-clock (default); **GUIDE**: `harness/GUIDE.md`

## Methodology

### Step 1: Read GUIDE, the prober role, TITLES and SEED

Skim TITLES once so you know the shape of what exists; grep it before designing every experiment.

### Step 2: Pick threads, ask the controller question

For each thread in the seed ask: "what would break or confuse a naive reconciler here?" - a loop that re-applies on
every reconcile, a finalizer, an adoption of an existing resource, a delta computed from a stale read, a fixed sleep.
Design the smallest experiment that answers the question; prefer experiments that distinguish between two plausible
controller strategies.

### Step 3: Novelty check

Before running: `grep -i` the operations and key nouns in TITLES. Already covered -> skip, or extend only if you add a
genuinely new aspect (another state, code, boundary or cause); then say so in `notes` ("extends <id> with ...") and
put the id in `related`. Re-proving known things scores nothing.

### Step 4: Run, follow surprises, respect the time box

6-12 experiments in TIME_BOX; several small experiments may share one `probe.py` under
`<resource>/creative/<variant>` (or `service/creative/<variant>`). Follow a surprise for a few extra calls (boundary,
state dependence, exact message) rather than starting a new thread. Stop at the time box; report what is running.

### Step 5: Record

`lab.finding(...)` with `tags: [creative, <seed-name>]`, `hypotheses: []`, `handling: "unhandled"`. What counts as a
finding: a behavior a controller must handle that no existing title states, a documented behavior that does not hold, a
200 that is silently dropped or rolled back, an undocumented cooldown/quota and its key, a deterministic 5xx or a
4xx-with-side-effect, an error message whose class (retry vs permanent) differs from its code. Negative results
("tried X, nothing unusual") go in the report, not as findings, unless a naive author would assume otherwise.

### Step 6: Import and report

`semantics finding import <svc> <probe-id>` per probe; clean up; `semantics probe status <svc>`. Reply (<= 40 lines):
experiments run (one line each: question -> answer), findings imported (ids), what you tried that yielded nothing,
one sentence on whether the seed was worth the time.

## Completion Criteria

- Every experiment passed the novelty check or is an explicit extension with `related`
- 6-12 experiments attempted within TIME_BOX, probes completed or reported running
- Findings imported with `creative` tags; account clean except what the report names
- Report delivered

## Constraints

- BLIND: no controller repository, no `ground-truth.yaml`, `candidates.md`, `scorecard.md`, `scoring/`
- All prober constraints apply (naming, registration, locks, polling limits, no generic `pkill`, own directories only)
- Do NOT exceed TIME_BOX by more than one running experiment
- Do NOT re-prove existing titles; do NOT pad with data-plane experiments
- Do NOT write account ids or profile names into findings
